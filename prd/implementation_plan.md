# Реализованный технический стек и архитектура

Статус документа: актуализирован по состоянию на 29 августа 2026 года.

## 1. Технический стек

### 1.1 Приложение

- **Python 3.12.13** — версия production-образа в `Dockerfile`.
- **aiogram 3.30.0** — асинхронный Telegram Bot API и работа с forum topics.
- **google-genai 2.8.0** — прямой доступ к Gemini API и native function calling.
- **SQLAlchemy 2.0.48 + aiosqlite 0.22.1** — асинхронный доступ к SQLite.
- **Alembic 1.16.5** — миграции базы данных.
- **gspread 6.2.1** — интеграция с Google Sheets через service account.
- **Docker + Docker Compose** — production-развёртывание.

`requirements.txt` является полным lock-файлом с точными версиями прямых и
транзитивных зависимостей.

### 1.2 LLM-интеграция

- Используется один провайдер: **Google Gemini API**.
- Единственная рабочая модель: **`gemini-3.5-flash-lite`**.
- Модель задаётся через `GEMINI_MODEL`; значение по умолчанию —
  `gemini-3.5-flash-lite`.
- Автоматического model fallback, второго провайдера и каскада моделей нет.
- LangChain и LangGraph не используются: текущий одношаговый диспетчер проще и
  прозрачнее реализовать прямым вызовом Gemini API.
- Все смысловые сообщения, включая благодарности, отправляются в модель.
  Регулярные выражения не принимают бизнес-решения.

## 2. Ядро обработки сообщения

Telegram является транспортной обёрткой над независимым ядром:

1. `bot/handlers.py` принимает сообщение, проверяет rate limit и состояние
   админ-темы, сохраняет историю и формирует нейтральный `TurnRequest`.
2. `assistant/engine.py` делает ровно один запрос к
   `gemini-3.5-flash-lite`.
3. Модель обязана выбрать ровно один tool и не может отправить клиенту
   свободный текст.
4. Guard продукта (`apply_product_guard` в `llm/tool_executor.py`) может
   подменить выбор модели: в диалоге о вакансии рекламный календарь
   недоступен, а собирать текст платной вакансии нельзя, пока клиенту не
   названы оба варианта с ценой. Продукт определяется по каноническим репликам
   самого бота, поэтому проверка детерминированная (ADR-0005).
5. `llm/tool_executor.py` проверяет имя и аргументы tool, подставляет доверенный
   Telegram-контекст и исполняет действие не более одного раза.
6. Клиент получает каноническую реплику из `bot/replies.py` или результат
   доверенной интеграции, например список дат из Google Sheets.

Технические команды `/start` и `/help`, а также медиа без подписи остаются на
уровне Telegram-обёртки: им не нужна смысловая классификация. Любой обычный
пользовательский текст передаётся в `AssistantEngine`.

Разделение маршрутизации и исполнения предотвращает повторное бронирование или
создание двух задач при ошибке модели. `telegram_id`, контакт и ссылка на
админ-диалог всегда берутся из серверного контекста, а не из аргументов LLM.

## 3. Локальные eval без Telegram

Интерактивный режим:

```bash
python scripts/eval_assistant.py --interactive
```

Пакетный прогон JSONL-датасета:

```bash
python scripts/eval_assistant.py \
  --dataset tests/fixtures/dialog_cases.jsonl \
  --metrics
```

`DryRunToolExecutor` вызывает модель по-настоящему, но не изменяет Google
Sheets, Telegram и другие внешние системы. Результаты сохраняются в
`eval_runs/<timestamp>/results.csv` и `summary.json`. CSV содержит поля для
ручных оценок `manual_score` и `manual_notes`. Оценка 4–5 считается принятой;
`expected_tools` задаёт несколько допустимых эквивалентных маршрутов.

`scripts/import_telegram_export.py` создаёт обезличенные JSONL-кандидаты из
Telegram Desktop export. Исходный export не копируется в проект, а результат
импорта требует ручной проверки перед добавлением в fixtures.

## 4. Контекст диалога

- История хранится в SQLite в таблице `messages_history`.
- В один модельный запрос передаются до 39 последних сохранённых сообщений
  **текущей сессии** плюс текущее сообщение. Сессия обрывается на первой паузе
  дольше трёх дней между сообщениями (`assistant/session.py`, ADR-0008).
  Без этого история многомесячной давности управляла бы новым вопросом:
  guard продукта читает историю, не глядя на её возраст. В БД старая
  история сохраняется, отсекается только то, что уходит в модель.
- Роли истории нормализуются в provider-neutral формат `user`, `assistant` и
  `admin`; реплики менеджера помечаются в контексте отдельно.
- Параллельные LLM-запросы одного пользователя сериализуются пользовательским
  lock, чтобы не нарушать порядок сообщений и side effects.

## 5. Схема SQLite

### `clients`

Компания рекламодателя: `id`, `name`, уникальный nullable `inn`, `created_at`,
`notes`. **Не используется:** код в таблицу не пишет. Удалять не стали —
деструктивная миграция при старте контейнера рискованнее, чем лишняя таблица
(ADR-0010).

### `representatives`

Telegram-представитель компании: `telegram_id`, nullable `client_id`,
`username`, `first_name`, `role`. `client_id` и `role` не заполняются
(ADR-0010).

### `admin_topics`

Связь представителя с Telegram forum topic: `topic_id`, уникальный
`telegram_id`, `status`, nullable `escalated_at`. Рабочие состояния: `active`,
`waiting_human`, `human_mode`.

`escalated_at` — момент последней эскалации. Если клиент в `waiting_human`
пишет спустя больше 4 часов, менеджерам уходит повторное уведомление, а окно
перезапускается (ADR-0009). `NULL` у строк, созданных до колонки, считается
просроченным. Колонку добавила миграция `fdcc4873908b` — только `ADD COLUMN`,
без перестройки таблицы.

### `messages_history`

История диалога: `id`, `telegram_id`, `role`, `content`, `created_at`.

### `bot_settings`

Служебные key/value-настройки, включая актуальный ID темы эскалаций.

## 6. Google Sheets

Google Spreadsheet остаётся источником правды для календаря и задач по
документам.

### Лист `Календарь (Слоты)`

- чтение ближайших свободных дат;
- проверка одной или нескольких конкретных дат;
- бронирование с повторной проверкой статуса слота непосредственно перед
  записью;
- окно бронирования ограничено текущим и двумя следующими месяцами;
- пользовательские значения экранируются от formula injection.

### Лист `Задачи (Документы)`

- создание задач на счёт, договор или акт;
- сохранение компании, ИНН, контакта, реквизитов и ссылки на диалог;
- уведомление менеджера без перевода клиентского диалога в human mode.

## 7. Telegram и медиа

- Приложение работает через long polling.
- Для каждого пользователя создаётся отдельная тема в закрытой супергруппе.
- Текст клиента и ответы бота зеркалируются в тему.
- Медиа пересылаются в тему и не сохраняются в SQLite.
- При `handover_to_admin` бот переходит в `waiting_human`; после ответа
  менеджера — в `human_mode`; команда `/close` возвращает `active`.

## 8. Production и безопасность

- Контейнер запускается от UID/GID `10001:10001`.
- Root filesystem read-only, Linux capabilities удалены,
  `no-new-privileges` включён.
- Writable mount используется только для `/app/data`; credentials JSON
  подключается read-only.
- Перед обновлением VPS обязателен проверенный backup SQLite.
- Миграции Alembic применяются автоматически при старте контейнера.
